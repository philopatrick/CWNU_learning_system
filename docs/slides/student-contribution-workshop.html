Slide 2 · Vocabulary

Know The Words Before The Workflow

GitHub basics

  • Repository: the project home on GitHub.
  • Clone: your local copy on your computer.
  • Fork: your personal GitHub copy of the project.
  • Branch: a separate line of work for one task.

Collaboration basics

  • Commit: a saved checkpoint with a message.
  • Pull Request: a request to merge your branch.
  • Review: comments and approval from maintainers.
  • Merge: the final step that brings code into main.
Slide 3 · SSH

Set Up Git SSH Once

SSH is the cleanest way to push and pull from GitHub. Set it up once and reuse it across all projects. 

ssh-keygen -t ed25519 -C "your-email@example.com"
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519
cat ~/.ssh/id_ed25519.pub
ssh -T git@github.com
Add the public key to GitHub under Settings → SSH and GPG keys. Expected result: successful GitHub authentication.
Slide 4 · Fork Model

Students Should Default To Fork + PR

1. Fork

Create your own GitHub copy of the repository.

2. Clone

Clone your fork to your local machine.

3. Upstream

Add the main class repository as upstream.

4. Branch

Create one branch for one task.

5. PR

Push to your fork and open a pull request.

git clone git@github.com:YOUR_USERNAME/CWNU_learning_system.git
cd CWNU_learning_system
git remote add upstream git@github.com:ORIGINAL_OWNER/CWNU_learning_system.git
git remote -v
Slide 5 · Branching

One Branch, One Job

Good branch names

  • docs/student-onboarding
  • fix/homework-empty-state
  • feature/playground-language-cards

Branch rule

  • Do not code on main.
  • Do not mix unrelated changes.
  • Keep PRs small enough to review.
git checkout main
git fetch upstream
git merge upstream/main
git checkout -b docs/student-onboarding
Slide 6 · Commits

Make Commits Easy To Read

Good commit prefixes

  • docs:
  • feat:
  • fix:
  • test:
  • refactor:

Examples

  • docs: add contribution handbook
  • fix: normalize attendance response
  • feat: add teacher summary cards
git add .
git commit -m "docs: add contribution handbook"
Slide 7 · PRs

Open A Pull Request With Context

A PR is not just code. It is an explanation to another engineer about what changed and why.

PR should include

  • what changed
  • why it changed
  • how it was tested
  • screenshots for UI work

Before review

  • run relevant checks
  • remove secrets
  • keep the PR focused
  • read your own diff once
git push -u origin docs/student-onboarding
gh pr create
Slide 8 · Review

Review Is Normal, Not Personal

Open PR

Ask for review with a clear title and description.

Receive comments

Read carefully. Do not reply defensively.

Update branch

Push follow-up commits to the same branch.

Approve

The maintainer confirms the branch is ready.

Merge

The maintainer merges, often with squash merge.

# or API key flow
printenv OPENAI_API_KEY | codex login --with-api-key

Slide 10 · Class Rules

Project Rules For Students

Do

  • keep branches focused
  • write readable commit messages
  • test before opening a PR
  • ask questions early

Do not

  • push directly to main
  • commit secrets or .env files
  • open giant mixed PRs
  • use AI output blindly
